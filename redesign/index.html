Project A · UC Santa Cruz AIEA Lab

Fault Recovery in RL Locomotion Through Online Residual Adaptation

Can a small correction module, updated during execution, restore a quadruped's gait after a hardware fault without retraining the policy underneath?

01 / 06

Premise

01 — Premise

Policies are trained on robots that never break.

In the real world motors weaken, joints seize, and sensors start reporting values that aren't true. A locomotion policy trained only under ideal conditions has never once been shown what failure feels like — so it has no response to it.

02 — Apparatus

A quadruped you can break on purpose.

Twelve revolute joints in PyBullet, physics at 240 Hz stepped down to 60 Hz control. PPO trained across ten seeds at 1.5M timesteps — all ten converged to a usable gait, so every one of them is in the experiment.

Every seed reached a usable gait on this run, so none were held out and all ten are aggregated above — the convergence rate is a reported result either way, since it characterises how reliably this setup produces a usable policy.

03 — Injection

At step 200, something fails.

Five fault families on a matched seed set, so every fault type is compared against identical initial conditions. Three corrupt the physics — what the robot can do. Two corrupt the observations — what the robot knows.

torque_limitjoint_lockactuation_delaysensor_dropoutsensor_noise

04 — Method

Correct around the fault, don't retrain through it.

A small residual module sits between the frozen base policy and the actuators, updating online. The seized joint stays seized — the correction redistributes the gait around it. Measured against two bounds: no adaptation, and full retraining.

Not built yet — this is the hypothesis the apparatus exists to test.

05 — Measurement

First, build an instrument you can trust.

The original recovery criterion latched onto the first instantaneous velocity crossing and scored ~100% recovery on every fault — including 100% recovery alongside a 36.5% fall rate, which cannot both be true. It was rebuilt: velocity smoothed over a 30-step causal window, degradation has to be observed before recovery can be, the speed must hold for 30 consecutive steps, and a trial that falls is never scored as recovered.

Every recovery number predating that change was discarded.

06 — Finding

The faults separate cleanly.

Unadapted recovery runs from 1.2% on actuation_delay to 82.3% on sensor_noise. Every actuation-side fault is less recoverable than both sensor-side faults, with no overlap — which makes the physics/sensor distinction a measured property of the system rather than a labelling convention, and a defensible axis for the H3 generalization split.

Real headroom for an adaptation method to demonstrate an effect.

Recovery is conditional on degradation — of the trials where the fault measurably slowed the robot, the fraction that returned to pre-fault speed and held it. Trials the fault never affected are counted under Degraded rather than scored as recoveries. torque_limit and joint_lock are the highest-power test cases: recovery sits mid-range at 43.1% and 53.7%, so an adaptation method has room to move it without running into a floor or a ceiling. actuation_delay is the severe end — it topples the robot in 78.5% of trials and almost never recovers.

Project B · Protein design copilot

Codon Lab

Turns a plain-language protein engineering goal into a ranked, defensible list of specific mutations — and refuses to guess when it does not know.

The models that could help a wet-lab protein engineer are Python repos with CUDA requirements, not tools. So bench scientists either do not use them, or run a colleague's notebook once and never trust the output enough to spend $4,000 of ordering budget on it. The gap is not capability. It is trust.

Three invariants.

01 — Parse, then confirm

Never silently interpret.

The user types a goal in English. It is parsed into an explicit structured objective and shown back as editable chips. Nothing runs until the user confirms that parse. The gate lives in the service layer rather than on a screen, because the job queue is a second caller, and a check that lives only in the UI is a check the API does not have.

The parser has no scientific authority. Every field is optional, and an absent field means not stated, never a default. A parse that quietly filled in 50 °C because thermostability usually means about that would be indistinguishable, on screen, from a number the scientist chose.

02 — Provenance

Every number is traceable.

Any score traces to which model, which version, which weights hash, which inputs, which run, at what time — in two clicks, counted literally. Enforced in the database, where the model version and the run are both non-null, and in the type system: a predictor returns a value carrying no run and no model version, so it is structurally incapable of producing an untraceable number.

The weights hash is taken over the checkpoint bytes actually loaded, never a placeholder. A made-up hash is indistinguishable from a real one in a provenance trail, which turns the whole claim into a lie.

03 — Fabrication

Never invent a scientific number.

Exactly one module is permitted to invent a number, and it declares itself. That single flag raises a persistent amber bar and badges every individual number with a footnoted mark. Unavailable means an em dash with a tooltip explaining why — never an imputed value, never a blank that could pass for zero. A predictor that cannot run says so and produces nothing; it never falls back to another provider.

No claim rests on a rank statistic alone.

Agreement with published solvent-accessibility output was supposed to validate the van der Waals radii set. It cannot. A correlation statistic is invariant to the transform that produces the error it is meant to catch: swapping the radii set for a uniform radius moved 8 residues across a region boundary while raising correlation to r = 0.998. The test would have passed more convincingly while the answer got worse.

So the scorecard reports a rank metric and an error metric and a bias term. A predictor offset by a constant +2 kcal/mol scores Spearman 1.0000 and precision@10 of 1.0 while being useless for the decision the user is actually making. The gate constructs exactly that predictor and asserts it is caught only by the bias term, at −2.00 kcal/mol.

What is not verified.

Tracked as carefully as the code, because on this project the distinction is the product.

  • Frame rate. Constant work per scroll update is asserted in CI — 10,000 rows mount the same number of table rows as 100. Measured once in a real browser on a 10,450-row ranking: 32 rows, 772 DOM nodes, 0.8 ms for a synchronous scroll. That is the property 60 fps rests on. It is not a frame rate, and none is claimed.
  • The structure viewer. It reports ready and its coordinates come from our own API, but everything it draws goes to a canvas. Nothing about the image is verified.
  • The language-model goal parser has never run against the live API. No key is configured, so every parse falls back to the deterministic rule parser and is badged as such.
  • Absolute stability accuracy. The predictor's position mapping and sign convention are checked; its values are compared against no external benchmark.
  • No screen has been looked at by a human. Rendering was verified by reading the DOM and by driving it in a real browser. That establishes correct, not good.

Known gaps.

  • Primers and the one-page PDF are not built. The blocker is gone and the chemistry is decided; the designer itself remains.
  • A run abandoned mid-flight stays running forever. Nothing reaps it, and the idempotency index then blocks an identical re-run.
  • Uncertainty intervals. The stability predictor has no per-variant uncertainty to give, so it reports the point estimate with the reason stated rather than dressing a benchmark error as a per-variant interval. The requirement is formally unmet, visibly.
